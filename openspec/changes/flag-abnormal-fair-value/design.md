# Design

## Context

ดู proposal.md (Why) หน้า `web/app/stocks/[symbol]/page.tsx` วาดสองตารางจากแถวของ `ev.fair_value.items` และ `ev.fair_value.gate.items` ซึ่งมี `mos` อยู่แล้ว เกณฑ์ MoS < −100% มีอยู่สองที่แล้ว คือ `ABNORMAL_MOS` ใน `engine/shortlist/backtest.py` และ skill `stock-sanity-check`

## Goals / Non-Goals

**Goals:**
- ผู้ใช้เห็นทันทีว่าเกณฑ์ไหนไม่ควรอ่านเป็นราคาเป้าหมาย
- ใช้ได้กับ evaluation ทุก run ที่เก็บไว้แล้ว

**Non-Goals:**
- แก้สาเหตุ (peer group, สมมติฐานของ Justified PBV)

## Decisions

### D1: คิดป้ายใน web จาก `mos` ไม่เพิ่ม field ใน engine

เพิ่มฟังก์ชันใน `web/lib/gates.ts` ที่รับ MoS แล้วบอกว่าติดป้ายไหม (`mos !== null && mos < -1`) ทั้งสองตารางเรียกฟังก์ชันเดียวกัน

- ทางเลือก: engine เพิ่ม `abnormal` ในแต่ละ item ไม่เลือก เพราะ evaluation ของ run เก่าไม่มี field นี้ ต้องรัน batch ใหม่ และต้องแก้ทั้ง engine และ type ใน web เพื่อแสดงป้ายที่เป็นเงื่อนไขเดียว
- ข้อแลกเปลี่ยน: ตอนนี้เกณฑ์ −100% อยู่สามที่ (backtest, skill, web) ใส่ comment ที่ค่าคงที่ใน web ว่าต้องตรงกับ `ABNORMAL_MOS`

### D2: ป้ายเป็น `Tag` ในคอลัมน์ที่มีอยู่ พร้อม `Tooltip`

ใน panel ป้ายอยู่ในคอลัมน์หมายเหตุ ในตาราง gate อยู่ต่อท้ายข้อความ MoS ใช้ `Tag` และ `Tooltip` ที่หน้านี้ใช้อยู่แล้ว ข้อความ tooltip: peer ใน sector อาจทำธุรกิจต่างกัน หรือสูตรสมมติ ROE และ PE คงที่ ให้ดู PE band ของหุ้นเองประกอบ

- ทางเลือก: ซ่อนตัวเลขหรือแสดงเป็น N/A ไม่เลือก เพราะผู้ใช้ให้แสดงตัวเลขไว้ และ N/A แปลว่าคำนวณไม่ได้ ซึ่งไม่จริง
- ทางเลือก: ทำให้ทั้งแถวเป็นสีจาง ไม่เลือก เพราะสีอย่างเดียวไม่บอกเหตุผล และอ่านยากใน dark mode

## Risks / Trade-offs

- [กรณีเลวร้าย: ป้ายทำให้ผู้ใช้คิดว่าหุ้นที่ติดป้ายถูก ทั้งที่ตลาดอาจให้ราคาแพงจริง (BEM: แม้ r 8% ก็ได้ fair value ราว 3.65)] → tooltip บอกว่าป้ายแปลว่าเกณฑ์นั้นอ่านไม่ได้ ไม่ได้แปลว่าหุ้นถูก
- [หุ้นที่ MoS −90% ไม่ติดป้าย ทั้งที่อาจมีปัญหาเดียวกัน] → เกณฑ์เดียวกับ backtest และ sanity check เพื่อให้นับตรงกัน ถ้าจะเปลี่ยนต้องเปลี่ยนทั้งสามที่
- [เกณฑ์ใน web กับ backtest ไม่ตรงกันหลังมีคนแก้ที่เดียว] → comment ที่ค่าคงที่ และ test ที่ขอบ −100%
