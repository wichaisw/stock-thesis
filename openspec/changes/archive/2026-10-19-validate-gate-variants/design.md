# Design

## Context

ดู proposal.md - Why

- `backtest.evaluate_date` รัน `quality.evaluate` และ `fair_value.evaluate` ของ engine ณ แต่ละวันสิ้นไตรมาส แล้วติด flag `candidate`, `candidate_median`, `relative` ต่อแถว `groups` อ่าน flag เป็นกลุ่ม และ `excess`/`uncertainty` คิด excess ต่อวันที่ พร้อม bootstrap CI ที่ seed คงที่
- backtest ไม่มี CDC เลย (ข้อจำกัดในไฟล์ผล) candidate ของ backtest = quality + gate ด้าน fair value
- `batch.evaluate_stock` เรียก `cdc.evaluate` แล้วส่ง `cdc_result["slow"]` ให้ `risk_reward` เท่านั้น `fair_value.py` และ `quality.py` ไม่ import `cdc`
- วันที่ทดสอบ 22 วัน (2021Q1–2026Q2) ผลรอบ 2026-10-15: candidate excess +1.7% t 3.25 การแบ่ง 2021–23 / 2024–26 เคยทำใน spike ของ gate-on-proven-methods (t 2.17 / 2.46)

## Goals / Non-Goals

**Goals:**
- วัด variant ทุกตัวด้วยตัววัด, seed และ baseline เดียวกับกลุ่ม candidate เดิม เพื่อให้เทียบกันตรงๆ
- เกณฑ์ตัดสิน variant ถูกเขียนใน code และ spec ก่อนรัน ไม่ใช่เลือกหลังเห็นผล

**Non-Goals:**
- ไม่ใส่ CDC ใน backtest
- ไม่ทำ walk-forward หลายหน้าต่าง (22 วันที่น้อยเกินจะแบ่งมากกว่าสองช่วง)

## Decisions

### D1 variant เป็นรายการคงที่ใน `backtest.py` ไม่ใช่ config

variant แต่ละตัวคือชื่อ + quality config ที่ `replace` จาก `cfg.quality` + ฟังก์ชัน gate ที่รับ MoS ของ gate methods ที่คำนวณได้ แล้วคืน True/False `evaluate_date` ติด flag `variant:<ชื่อ>` ต่อแถว ใช้ `groups` เดิมอ่าน

- ทางเลือก: ใส่ variant ใน `engine/config.yaml` → ไม่เอา เพราะ variant เป็นการทดลองของ backtest ไม่ใช่ค่าที่ batch ใช้ การใส่ใน config ทำให้ดูเหมือนเป็นตัวเลือกจริงของระบบ
- ทางเลือก: ให้ skill script รับ variant ทาง CLI → ไม่เอา ผลแต่ละรอบจะเทียบกันไม่ได้ถ้ารายการ variant เปลี่ยนตามการรัน

### D2 ตีความ Option A และ B เมื่อคำนวณได้ gate method ตัวเดียว

Doc 2 บอกแค่กรณี peer PE คำนวณไม่ได้ (Justified PBV ตัวเดียวต้อง ≥ 12%)
- Option A: คำนวณได้ตัวเดียว (ตัวไหนก็ได้) ต้อง ≥ 12% เหมือนกันทั้งสองตัว เพราะ gate ปัจจุบันก็ไม่แยกว่าตัวไหนหายไป
- Option B: ต้องคำนวณได้ทั้งสองตัว ถ้าได้ตัวเดียวถือว่าไม่ผ่าน เพราะค่าเฉลี่ยของสองตัวไม่มีความหมายเมื่อมีตัวเดียว และหลักของระบบคือคำนวณไม่ได้ต้องไม่กลายเป็นผ่าน
- ทางเลือก: Option B ตัวเดียวใช้ ≥ 8% → ไม่เอา เป็นเกณฑ์ที่หลวมกว่า rule ปัจจุบัน (10%) โดยไม่มีที่มา
- ทางเลือก: Option A ตามตัวอักษร (เฉพาะ Justified PBV ตัวเดียว) → ไม่เอา ทำให้หุ้นที่มีแต่ peer PE ไม่ผ่านเสมอ ซึ่ง Doc 2 ไม่ได้ตั้งใจ

### D3 แบ่งสองช่วงตามปีปฏิทิน: 2021Q1–2023Q4 (12 วันที่) และ 2024Q1–2026Q2 (10 วันที่)

ใช้จุดแบ่งเดียวกับ spike ของ gate-on-proven-methods เพื่อเทียบได้ และแต่ละช่วงยังมีวันที่พอคิด CI
- ทางเลือก: walk-forward (เลือกบน 2021–23 แล้ววัดบน 2024–26) → ไม่เอา method ถูกเลือกจากทั้งช่วงไปแล้ว การทำเป็น walk-forward ตอนนี้จะดูเป็น out-of-sample ทั้งที่ไม่ใช่ การเรียกตรงๆ ว่า "ความคงที่ข้ามช่วง" ซื่อตรงกว่า
- ทางเลือก: แบ่งตามสภาวะตลาด (SET ขึ้น/ลง) → ไม่เอา ต้องนิยามสภาวะเอง ซึ่งเป็นการเลือกหลังเห็นข้อมูลอีกชั้น

### D4 เกณฑ์ตัดสิน variant

variant "ผ่าน" เมื่อ (1) excess เฉลี่ย 63 วันสูงกว่ากลุ่ม candidate ในทั้งสองช่วง และ (2) ช่วงความเชื่อมั่น 95% ของ excess เฉลี่ยทั้งช่วงของ variant ไม่คร่อม 0 (ขอบล่าง > 0) และ (3) candidate เฉลี่ย ≥ 3 ตัวต่อวันที่ และมี candidate ≥ 80% ของวันที่ทดสอบ (ผู้ใช้เพิ่ม 2026-10-19 กัน variant ที่ชนะด้วยหุ้นไม่กี่ตัวโดยบังเอิญ) คิดจากตารางผลรวมเดิมที่นับค่าผิดปกติ ผลนี้เป็นข้อมูลให้ผู้ใช้ ไม่เปลี่ยน default เอง

ตารางแสดงผลต่าง excess ต่อวันที่ (variant − candidate) แบบจับคู่วันที่ พร้อม CI เป็นข้อมูลประกอบ ไม่ใช่ส่วนของเกณฑ์ เพราะผู้ใช้อนุมัติเกณฑ์ข้างบนไว้แล้ว

- ทางเลือก: ใช้ CI ของผลต่างจับคู่เป็นเกณฑ์ → เข้มงวดและถูกหลักกว่า แต่ไม่ใช่เกณฑ์ที่ตกลงไว้ จึงแสดงไว้ให้เห็นแทน
- ทางเลือก: เลือก variant ที่ excess สูงสุด → ไม่เอา เป็นการ optimize บนข้อมูลชุดที่ใช้วัด

### D5 test ความเป็นอิสระของ CDC อยู่ระดับ `batch.evaluate_stock`

รัน `evaluate_stock` สองครั้งด้วยข้อมูลเดียวกัน ต่างกันแค่ `cfg.cdc` (เช่น fast 12/slow 26 กับ 5/35) แล้วยืนยันว่า `quality` และ `fair_value` (รวม `gate`) เท่ากันทุกค่า และ `cdc` ต่างกันจริง อีก test สลับกัน: เปลี่ยน `cfg.fair_value` แล้ว `cdc` เท่าเดิม `risk_reward` และ `inclusion` ไม่ถูกเทียบ เพราะใช้ CDC โดยตั้งใจ (stop จาก Slow EMA, state ใน candidate rule)
- ทางเลือก: test แบบ static ว่า `fair_value.py`/`quality.py` ไม่ import `cdc` → ไม่เอาเป็นหลัก จับได้แค่ import ตรง ไม่จับการส่งค่า CDC ผ่าน argument ใน batch

## Risks / Trade-offs

- [ความคงที่ข้ามช่วงไม่ใช่ out-of-sample] method และ 10% ถูกเลือกจากทั้งสองช่วงแล้ว variant ที่ผ่านเกณฑ์ D4 ก็ยังเป็น in-sample → ไฟล์ผลและ SKILL.md เขียนข้อนี้ตรงๆ ข้อมูลที่ไม่เคยเห็นจริงคือ `candidate_history` ตั้งแต่ 15 ต.ค. 2026 (change แยก)
- [เปรียบเทียบหลายครั้ง] variant 7 ตัว × 2 ช่วง ราว 1 ใน 20 ของ CI จะไม่คร่อม 0 โดยบังเอิญ → เกณฑ์ D4 ต้องผ่านทั้งสองช่วงพร้อมกัน และเพิ่มข้อนี้ในข้อจำกัดของไฟล์ผล
- [variant ที่เข้มขึ้นมี candidate น้อย] MoS 25% อาจเหลือไม่กี่ตัวต่อวันที่ excess แกว่งมากและอาจชนะโดยบังเอิญ → เกณฑ์ D4 ข้อ (3) ตัด variant ที่ candidate น้อยเกินไป ค่า 3 ตัวและ 80% ตั้งเองไม่ได้มาจากข้อมูล จึงแสดงตัวเลขจริงให้ผู้ใช้เห็นด้วย
- [worst case] variant หลวม (Option A/B) ผ่านเกณฑ์ D4 ด้วยโชค แล้วถูกใช้เป็น default → candidate list รับหุ้นที่ method หนึ่งบอกว่าแพง 10% ในตลาดจริง การป้องกันคือ change นี้ไม่เปลี่ยน default และ change ถัดไปต้องผ่านการตัดสินใจของผู้ใช้
- [ผลต่างจาก batch] backtest ใช้งบ thaifin อย่างเดียวและ liquidity จาก `engine/config.yaml` (10 ลบ.) ไม่ใช่ค่าที่บันทึกบนเว็บ (3 ลบ.) → ทุก variant ใช้ฐานเดียวกัน จึงเทียบกันได้ แต่ตัวเลขสัมบูรณ์ไม่ใช่ของ batch จริง
- [ผลเดิมต้องไม่เปลี่ยน] การเพิ่มกลุ่มอาจทำให้ seed ของ bootstrap หรือลำดับกลุ่มเลื่อน → task ยืนยันว่าทุกแถวเดิมของไฟล์ผลเท่ากับรอบ 2026-10-15 เมื่อใช้ cache เดียวกัน
