# Design

## Context

ดู proposal.md (Why) ตอนนี้ batch ประเมินแค่วันนี้: `batch.collect` ดึงราคา 1 ปี (`YahooPrices`), งบทุกไตรมาสจาก thaifin (ย้อนถึง 2010) และ market cap รายไตรมาส (`fetch_market_caps`, `history_period` 6 ปี) แล้วเรียก `fair_value.evaluate(quarterly, price, peer_pes, cfg, caps)` และ `quality.evaluate(quarterly, sector, cfg)` ซึ่งเป็น pure function ที่ใช้แถวสุดท้ายของข้อมูลเป็น "ปัจจุบัน" DB เก็บ evaluation ของ run ล่าสุดเท่านั้น จึงย้อนดูผลเก่าจาก DB ไม่ได้

ข้อมูลที่ตรวจแล้ว (15 ต.ค. 2026): thaifin CPALL มี 2010Q1–2026Q4, จำนวนหุ้นจาก yfinance (`get_shares_full`) เริ่ม พ.ย. 2018, `^SET.BK` บน yfinance มีแค่วันล่าสุด (ไม่มีประวัติ)

## Goals / Non-Goals

**Goals:**
- วัดด้วย code จริงของ engine ทุกครั้ง แก้สูตรแล้วรันซ้ำก็เห็นผลใหม่ทันที
- ผลรอบต่อรอบเทียบกันได้ (ไฟล์ markdown มี commit และค่าเกณฑ์)

**Non-Goals:**
- จำลองพอร์ต การเทรด หรือ CDC
- หาค่าเกณฑ์ที่ดีที่สุด (optimize) ทำแค่วัด

## Decisions

**D1 เรียก `fair_value.evaluate`, `quality.evaluate`, `quality.liquidity`, `fair_value.current_pe`/`peers_for` ตรงๆ กับข้อมูลที่ตัด ณ วันที่ทดสอบ**
ทางเลือกที่ไม่เลือก: เขียนสูตรซ้ำใน script (วัดของที่ไม่ใช่ของจริง และเพี้ยนไปเมื่อ engine เปลี่ยน), รัน batch ย้อนหลังผ่าน `collect` (ผูกกับ source ที่ดึงข้อมูลวันนี้ และเขียน DB) ข้อแลก: ถ้า signature ของ core เปลี่ยน backtest ต้องแก้ตาม test จะจับได้

**D2 ข้อมูล ณ วันที่ทดสอบ T (สิ้นไตรมาส)**
- งบ: เฉพาะไตรมาสที่ สิ้นไตรมาส + `catalyst.quarter_deadline_days` (Q4 ใช้ `annual_deadline_days`) ≤ T ใช้ค่าจาก config เดิม ไม่เพิ่มค่าใหม่ ที่วันสิ้นไตรมาสผลคือใช้งบถึงไตรมาสก่อนหน้าเสมอ
- market cap/จำนวนหุ้น/ปันผล: แถวไตรมาส ≤ ไตรมาสของ T
- ราคา: แท่ง ≤ T สำหรับ price และ liquidity
- peer PE: `current_pe` ของหุ้นที่ผ่าน liquidity ณ T ใน sector เดียวกัน เหมือน batch
ทางเลือกที่ไม่เลือก: วันประกาศงบจริง (ไม่มีแหล่งย้อนหลัง), lag คงที่ 1 ไตรมาส (ได้ผลเท่ากันที่สิ้นไตรมาส แต่ผิดถ้าวันทดสอบเปลี่ยน)

**D3 ตัดหุ้นที่ split, ปันผลเป็นหุ้น หรือ merge ออกทั้งตัว แทนการแปลงราคา (ผู้ใช้เลือก)**
ราคาและปันผลจาก yfinance ถูกปรับ split ถึงวันนี้ แต่ `shares`/`mkt_cap` ใน caps เป็นของ ณ ไตรมาสนั้น batch ไม่เจอปัญหาเพราะไม่มี split หลังวันนี้ แต่ใน backtest หุ้นที่ split หลัง T (เช่น SCAP) จะได้ MoS ผิดเป็นเท่าตัว จึงตัดหุ้นที่มี `Stock Splits` ≠ 0 วันใดก็ได้ในราคา 8 ปี (yfinance นับปันผลเป็นหุ้นเป็น split ด้วย) และหุ้นที่ส่วนผู้ถือหุ้นเปลี่ยนเกิน `fair_value.structure_change_threshold` ระหว่างไตรมาสติดกันในช่วงทดสอบ ส่วนหุ้นที่ market cap ขาดกลางช่วง lookback ณ T (ระหว่างไตรมาสแรกและไตรมาสสุดท้ายที่มี market cap ไตรมาสท้ายที่ขาดไม่นับ เพราะจะซ่อนงบที่รั่วจาก poison check) ข้ามแค่วันนั้น ไม่ใช้ `history_gap` ของ engine ตรงๆ เพราะจำนวนหุ้นเริ่ม พ.ย. 2018 ทำให้ทุกหุ้นถูก flag ที่ T 2021Q1–2023Q3 และเหลือวันที่ทดสอบ 11 จาก 22 วัน (ผู้ใช้เลือก)
ค่าประเมินผิดปกติ (เกณฑ์เดียวกับ `stock-sanity-check`: MoS < −100%, fair value > 5× ราคา) ไม่ตัด เพราะจะซ่อนความผิดพลาดจริงของ engine และทำให้ดูแม่นเกินจริง แต่แสดงแยกอีกตาราง
ทางเลือกที่ไม่เลือก: คูณราคาและ `dps_ttm` ด้วย factor ของ split หลัง T (ได้หุ้นมากกว่า แต่ถ้า factor ผิด MoS ผิดเป็นเท่าตัวโดยไม่มีใครเห็น), ข้ามเฉพาะวันที่ใกล้เหตุการณ์ (split หลัง T ทำให้ราคาเพี้ยนไม่ว่าห่างแค่ไหน)

**D4 ผลตอบแทนรวมปันผลจาก `Adj Close`, hit จาก `High`**
ดึงราคาด้วย `yf.download(auto_adjust=False, actions=True)` ครั้งเดียว 8 ปี ได้ทั้ง OHLCV (ใช้ `clean_prices` เดิม), `Adj Close` และ `Stock Splits` (ใช้ตัดหุ้นตาม D3) ผลตอบแทน 63 วัน = Adj Close(T+63)/Adj Close(T) − 1 ไม่ลำเอียงต่อหุ้นปันผลสูง hit = High สูงสุดในวันที่ 1–63 ≥ fair value (หุ้นที่เหลือไม่มี split ราคาจึงเทียบกันได้ตรงๆ) ทางเลือกที่ไม่เลือก: ใช้ `YahooPrices.fetch_prices` (ตัด Adj Close ทิ้ง ต้องแก้ adapter ของ batch), ผลตอบแทนจาก close ไม่รวมปันผล (method dividend yield จะดูแย่เกินจริง)

**D5 baseline คือ equal-weight ของหุ้นทุกตัวที่ประเมินได้ใน T เดียวกัน และ excess return เฉลี่ยรายวันที่ทดสอบ**
คำนวณ excess ต่อวันที่ทดสอบก่อน (กลุ่ม − baseline ของวันนั้น) แล้วสรุปข้ามวัน แต่ละไตรมาสจึงมีน้ำหนักเท่ากัน และตลาดขึ้นลงทั้งไตรมาสไม่ทำให้ผลดูดีหรือแย่ ทางเลือกที่ไม่เลือก: SET index (ไม่มีประวัติบน yfinance), TDEX (SET50 ETF มีบน yfinance แต่เป็นหุ้นใหญ่ ไม่ใช่ universe เดียวกัน เทียบแล้วผสมผล size เข้ามา), pool ทุกการประเมินรวมกัน (ไตรมาสที่มีหุ้นมากกว่ามีน้ำหนักมากกว่า)

**D6 pure logic ใน `engine/shortlist/backtest.py`, I/O ใน script ของ skill**
`backtest.py` มีการตัดหุ้น (D3), การตัดข้อมูล ณ T, การประเมินหนึ่งวัน, ตัววัด, poison check และ placebo (D10) และการสร้าง markdown โดยไม่ดึงข้อมูลเอง script `.agents/skills/fair-value-backtest/backtest.py` ดึงข้อมูล, cache, เรียก module และเขียนไฟล์ ทางเลือกที่ไม่เลือก: ทุกอย่างใน script ของ skill (`uv run pytest` ไม่ครอบคลุม), console script ใน `pyproject.toml` (เป็นเครื่องมือของนักพัฒนา ไม่ใช่ส่วนของแอป)

**D7 cache ข้อมูลดิบแบบ pickle ต่อหุ้นใน `engine/.cache/fv-backtest/` มี `--refresh`**
ดึงราคา 8 ปีทั้งตลาด + งบและ market cap ราว 400 ตัว ใช้หลายนาทีและเสี่ยง rate limit การรันซ้ำหลังแก้สูตรควรใช้เวลาไม่กี่วินาที ทางเลือกที่ไม่เลือก: ไม่ cache (ช้าทุกรอบ ข้อมูลเปลี่ยนระหว่างรอบเทียบ ทำให้เทียบก่อน/หลังแก้ code ไม่ได้), SQLite (เกินจำเป็น) ไฟล์ผลบอกวันที่ของ cache

**D8 ผลเต็มใน `docs/backtests/fair-value-<YYYY-MM-DD>.md` (commit, ผู้ใช้เลือก), README มีแค่สรุปและลิงก์**
ทางเลือกที่ไม่เลือก: README อย่างเดียว (ตารางยาวทุก method ทำให้ README อ่านยาก), `engine/backtests/` (ผลเป็นเอกสาร ไม่ใช่ส่วนของ engine), gitignore ไฟล์ผล (เสียประวัติไว้เทียบหลังแก้สูตร)

**D9 bucket MoS คงที่: < 0, 0–10%, 10–30%, ≥ 30%**
10% ตรงกับ `candidates.min_median_mos` default ทางเลือกที่ไม่เลือก: quintile (ขอบเปลี่ยนทุกรอบ เทียบรอบต่อรอบไม่ได้)

**D10 กัน look-ahead 3 ชั้น (ผู้ใช้เลือก)**
- poison check ทุกรอบ: สุ่ม 5 วันที่ทดสอบ (seed คงที่) ประเมินซ้ำโดยแทนทุกแถวหลัง T ของราคา งบ และ caps ด้วยค่าที่ผิดชัดเจน (เช่น ×1000) แล้วเทียบผลทุกค่า ต่างแม้ค่าเดียว = หยุด ไม่เขียนไฟล์ จับ bug ที่ตัดข้อมูลไม่หมดบนข้อมูลจริง ไม่ใช่แค่ข้อมูลสังเคราะห์ใน test
- placebo: สลับ MoS ระหว่างหุ้นในวันเดียวกัน (20 รอบ seed คงที่ เพราะรอบเดียวของ method ที่เลือกหุ้นน้อยแกว่งได้ ±4%) แล้วคำนวณ excess แบบเดียวกันและเฉลี่ย ควรใกล้ 0 ถ้าไม่ใกล้ แปลว่าวิธีวัด (baseline, การนับ) ลำเอียงเอง
- spot-check ด้วยมือเทียบ SET หนึ่งหุ้นหนึ่งวัน (task 3.2)

ทางเลือกที่ไม่เลือก: test ด้วยข้อมูลสังเคราะห์อย่างเดียว (ไม่ครอบคลุม path ที่ข้อมูลจริงผ่าน เช่น index ที่ไม่เรียงหรือ quarter label ข้ามปี), ตัดข้อมูลตั้งแต่ตอน fetch แยกต่อวันที่ทดสอบ (ต้องดึง 22 รอบ) ข้อจำกัดที่ทั้ง 3 ชั้นจับไม่ได้: งบ thaifin ที่ถูก restate ย้อนหลัง (ค่าที่ T เป็นค่าใหม่ ไม่ใช่ค่าที่ประกาศจริง ณ ตอนนั้น)

## Risks / Trade-offs

- **[แย่ที่สุด] bug look-ahead ทำให้ผลดูดีเกินจริง แล้วผู้ใช้เชื่อ fair value มากขึ้น** → D10 (poison check ทุกรอบ, placebo, spot-check) และ test ด้วยข้อมูลสังเคราะห์
- **[แย่ที่สุด] ปรับเกณฑ์ตามผลที่มีแค่ 22 วันที่ทดสอบ** → ไฟล์ผลบอกจำนวนวันและ % วันที่เป็นบวก และ change นี้ไม่แก้เกณฑ์ใด ๆ
- ตัดหุ้นที่ split/ปันผลเป็นหุ้นออก อาจตัดหุ้นโตเร็วที่จ่ายปันผลเป็นหุ้นบ่อย ผลจึงเป็นของหุ้นที่เหลือเท่านั้นและอาจลำเอียง → ไฟล์ผลแสดงจำนวนและ % ที่ตัดแยกตามเหตุผล ถ้าตัดเกินราว 30% ของหุ้นที่เคยผ่าน liquidity ให้บอกผู้ใช้ก่อนสรุปผล
- yfinance ไม่บันทึก split บางครั้ง หุ้นนั้นจะไม่ถูกตัดและ MoS เพี้ยน → ตารางค่าผิดปกติจะเห็น และ spot-check ว่า SCAP (par split 2022–2023) ถูกตัด
- survivorship bias: หุ้นที่ถูกถอนไม่มีใน yfinance ทั้งกลุ่มและ baseline ดูดีเกินจริง excess return ลำเอียงน้อยกว่าผลตอบแทนดิบ แต่ยังลำเอียง → เขียนในไฟล์ผล
- งบ thaifin เป็นค่าล่าสุดที่อาจถูก restate และ backtest ไม่ใช้งบ yfinance ที่ batch ใช้ปัจจุบัน → ผลอาจต่างจาก batch จริงในไตรมาสล่าสุด เขียนในไฟล์ผล
- จำนวนหุ้นเริ่ม พ.ย. 2018: วันที่ทดสอบช่วงต้นมี band แค่ราว 8 จุด (ไม่ถึง 20) → ไฟล์ผลแยกจำนวนที่ใช้ได้ต่อวันที่
- yfinance rate limit หรือคืนข้อมูลไม่ครบ → cache ทำให้ดึงซ้ำเฉพาะตัวที่ขาด ไฟล์ผลมีรายชื่อหุ้นที่ข้าม

## Migration Plan

ไม่มี ไม่แตะ DB และ batch ลบ change นี้ได้โดยลบ module, skill และไฟล์ผล
