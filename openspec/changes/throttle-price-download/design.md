# Design

## Context

`YahooPrices.fetch_prices` เรียก `yf.download(chunk, threads=True)` ทีละ 100 ตัว พัก `chunk_delay_seconds` (1 วินาที) ระหว่างชุด yfinance 1.7.0 แปลง `threads=True` เป็น `min(len(tickers), cpu_count × 2)` และรับ `threads` เป็นจำนวนเต็มได้ request ที่ถูกตัดจะ timeout ที่ 10 วินาทีแล้วหุ้นนั้นหายจากผล batch.py จึงเห็นเป็น "ไม่มีข้อมูลราคา" แล้วเรียก `reachable()` ซึ่งถือว่าคำตอบ HTTP ใด ๆ รวม 429 คือเครือข่ายใช้ได้ หุ้นจึง fail แบบไม่นับเป็น error ของเครือข่าย ตัวตัดวงจร 5 ตัวติดกันจึงไม่ทำงาน (ถูกต้องตาม spec แต่ไม่มีใครดึงซ้ำ)

`backtest_cdc.py` ใช้ `YahooPrices` ตัวเดียวกัน

## Goals / Non-Goals

**Goals:** ลด request พร้อมกันไปที่ Yahoo ในช่วงดึงราคา และกู้หุ้นที่โดนตัดชั่วคราวกลับมาในรอบเดียว โดยไม่เปลี่ยน interface ของ `PriceSource`

**Non-Goals:** หน่วงช่วงงบและ market cap, backoff หลายรอบ, แยกเหตุผล 429 ใน UI

## Decisions

### D1: จำกัด thread ผ่าน argument `threads` ของ `yf.download`
ส่ง `threads=price_threads` (int) แทน `True`
- ทางเลือก `threads=False` (ทีละ request): สุภาพกับ Yahoo ที่สุด แต่ช่วงราคาอาจยาวหลายนาทีในวันปกติ ผู้ใช้เลือก 4
- ทางเลือกลด `price_chunk_size`: จำนวน request พร้อมกันยังเท่าเดิมภายในชุด จึงไม่ตรงจุด คงไว้ 100

### D2: ดึงซ้ำหนึ่งรอบอยู่ใน `YahooPrices.fetch_prices`
หลังดึงครบทุกชุด ถ้ามีหุ้นที่ไม่ได้ราคาและรอบแรกได้ราคาอย่างน้อยหนึ่งตัว ให้พัก `retry_delay_seconds` แล้วดึงหุ้นที่ขาดอีกรอบด้วยลูปชุดเดิม รวมผลเข้า dict เดียวกัน
- ทางเลือกดึงซ้ำใน batch.py: batch และ `backtest_cdc.py` ต้องเขียนซ้ำกันสองที่ และ batch ต้องรู้เรื่องการจำกัดอัตราของแหล่งราคา ซึ่งเป็นรายละเอียดของ adapter
- ทางเลือก backoff หลายรอบ: ยังไม่มีหลักฐานว่ารอบเดียวไม่พอ เพิ่มเมื่อ log แสดงว่ารอบซ้ำได้คืนน้อย
- ไม่ดึงซ้ำเมื่อรอบแรกไม่ได้เลย: นั่นคือเครือข่ายล่มมากกว่าโดนจำกัดอัตรา การดึงซ้ำจะแค่ยืดเวลาก่อนที่ batch จะหยุด

### D3: log ผลของรอบซ้ำ
`fetch_prices` คืนแค่ dict ราคาเหมือนเดิม จำนวนที่ดึงซ้ำและได้คืนเก็บไว้ที่ attribute `last_retry` (`(asked, recovered)` หรือ `None`) batch.py log ต่อจากบรรทัด "ได้ราคา" ถ้ามีค่า แบบเดียวกับ `overlaid` ของ `PreferredStatements`
- ทางเลือกเปลี่ยน return type: กระทบ `PriceSource` protocol, fake ใน test และ `backtest_cdc.py` เพื่อข้อมูลที่ใช้แค่ใน log

### D4: ค่าใหม่ใน `batch` ของ config.yaml
`price_threads: 4`, `price_retry_delay_seconds: 30`, `chunk_delay_seconds` เปลี่ยนจาก 1.0 เป็น 3.0 ใน `Batch` ของ config.py มี `Field(gt=0)` ให้ `price_threads` และ `Field(ge=0)` ให้ `price_retry_delay_seconds` ไม่มี default ใน class เหมือน field เดิมของ `Batch` ที่ไม่ใช่ตัวตัดวงจร

## Risks / Trade-offs

- **กรณีแย่สุด: Yahoo ไม่ตอบทุก request (blackhole) แต่ DNS ใช้ได้** ทุก ticker timeout 10 วินาที ด้วย 4 thread รอบแรกใช้ราว 930 / 4 × 10 ≈ 39 นาที (เดิมราว 20 thread ≈ 8 นาที) และ `RunGuard` เช็คเวลาก่อนเริ่มช่วงดึงราคาเท่านั้น batch จึงเกินเพดาน 20 นาทีได้มากก่อนจะหยุดตอนเข้าช่วงงบ ถ้าบางตัวได้ราคา รอบซ้ำยังเพิ่มอีก → ยอมรับไว้ก่อนเพราะกรณีนี้ไม่เคยเห็น (เน็ตล่มที่เคยเจอเป็น DNS ซึ่ง fail ทันที) ถ้าเจอ ให้เพิ่มการเช็คเวลาระหว่างชุด ไม่ใช่ลด thread กลับ
- **4 thread อาจยังมากไปช่วงหลังตลาดปิด** → ปรับใน config ได้โดยไม่แก้ code และรอบซ้ำช่วยกู้ส่วนที่หาย ถ้ายังไม่พอ ทางที่ถูกกว่าคือย้ายเวลา cron
- **batch ปกติช้าขึ้น** ราว 1–2 นาที (พักเพิ่ม 2 วินาที × 9 ชุด และ thread น้อยลง) ยังห่างเพดาน 20 นาที ตัวเลขจริงวัดใน task 3.1
- **รอบซ้ำทำงานแทบทุก run**: หุ้นที่ไม่มีข้อมูลราคาจริง (ถูกถอนหรือหยุดพักการซื้อขาย) ไม่ได้ราคาทุก run จึงมีหุ้นให้ดึงซ้ำเกือบทุกครั้ง run ปกติจึงพักเพิ่ม 30 วินาทีและดึงหุ้นเหล่านี้ซ้ำโดยไม่ได้คืน → ยอมรับ เพราะต้นทุนราว 30 วินาทีกว่าต่อ run และไม่มีรายชื่อหุ้นไม่มีข้อมูลที่เชื่อถือได้ไว้ข้าม
- **รอบซ้ำซ่อนปัญหา**: ถ้า Yahoo จำกัดอัตราทุกวัน fail จะดูน้อยลง → log บอกจำนวนที่ดึงซ้ำทุก run จึงยังเห็นได้
