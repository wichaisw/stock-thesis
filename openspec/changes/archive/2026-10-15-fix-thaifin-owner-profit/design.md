# Design

## ผลลัพธ์ (15 ต.ค. 2026)

D3 หยุดงานก่อนแก้ code: EPS ของ thaifin ตรง SET แค่ 19 จาก 37 ปีของ 10 หุ้น (SAWAD, TOP, CPF, CHO ไม่ตรงทุกปี) และ 43 ไตรมาสใน 22 หุ้นไม่ถูกปรับตาม split (เช่น DELTA ×10, RAM ×5) ขณะที่ `net_profit` ตรงกำไรส่วนของบริษัทใหญ่บน SET 33 จาก 37 ปี ผลต่างที่วัดไว้ใน Context ส่วนใหญ่จึงมาจาก EPS ไม่ใช่ `net_profit`
- D1 (PE ต่อหุ้น) ไม่ทำ: จะทำให้ PE ผิดมากกว่าเดิม
- แผนสำรองของ D1 (ตัดไตรมาสที่ `net_profit` ต่างจาก EPS × จำนวนหุ้น) ไม่ทำ: ตัดไตรมาสที่ถูกทิ้งเพราะฝั่งที่ผิดคือ EPS
- D2, D4, D5 ไม่ได้ทำ ผู้ใช้เลือกคง PE ระดับบริษัทจาก `net_profit` ไว้ ผลตรวจอยู่ใน `engine/README.md`

ส่วนที่เหลือของเอกสารนี้คือแผนเดิมก่อนตรวจ เก็บไว้เป็นประวัติ

## Context

ดู proposal.md (Why) ตอนนี้ `fair_value.current_pe` และ `evaluate` คิด PE ระดับบริษัท: PE ย้อนหลัง = `mkt_cap` ÷ `net_profit` 4 ไตรมาส และ fair value = PE × `net_profit` 4 ไตรมาส ÷ จำนวนหุ้นล่าสุด (`latest_shares`) ส่วน `quarterly_market_cap` คิดราคาปิดสิ้นไตรมาสที่ปรับ split (`adjusted`) อยู่แล้วเพื่อหา dividend yield แต่ไม่ได้คืนค่านั้นออกมา batch ดึงราคาแค่ 1 ปี (`YahooPrices`) ส่วนราคา 5 ปีอยู่ใน `fetch_market_caps` เท่านั้น

วัดจาก cache ของ `backtest-fair-value` (15 ต.ค. 2026, 551 หุ้น ไตรมาสที่ |EPS| ≥ 0.10) อัตรา `net_profit` ÷ (EPS × จำนวนหุ้น ณ ไตรมาสนั้น) มี 4 แบบ:
- รวมส่วนของผู้ถือหุ้นส่วนน้อย: PTT 2022, SAWAD 1.1–1.3 แล้วกลับเป็น 1.0 ในปี 2024–2025
- แตกพาร์หรือปันผลเป็นหุ้น: COM7 2.0 จนถึง 2021 แล้ว 1.0 ตั้งแต่ 2022, HTC ราว 2.0 จนถึง 2023 แปลว่า thaifin ปรับ EPS ย้อนหลังตามจำนวนหุ้นปัจจุบัน แต่ HTC 2019Q1 เป็น 1.73 จึงยังไม่แน่ใจว่าปรับทุกไตรมาส
- หน่วยหรือสกุลเงิน: BANPU 0.02–0.05, CHO 0.05
- แกว่งสองทาง: TOP, CPF 0.5–1.5 บางไตรมาสติดลบ

## Goals / Non-Goals

**Goals:**
- PE ปัจจุบัน, PE band และ peer PE ใช้กำไรส่วนของบริษัทใหญ่ ตรงกับ P/E ของ SET
- ไม่ทำให้หุ้นที่เคยแตกพาร์ได้ PE ผิดเป็นเท่าตัว

**Non-Goals:**
- ROE, no-loss check, net profit YoY (ผู้ใช้เลือกให้คงเดิม)
- PBV band (ยังเป็นระดับบริษัท ส่วนผู้ถือหุ้นไม่มีปัญหาเดียวกัน: PTT ตรง SET)
- หาแหล่งกำไรส่วนของบริษัทใหญ่ย้อนหลังใหม่

## Decisions

**D1 PE ต่อหุ้น: ราคา ÷ EPS 4 ไตรมาส (ผู้ใช้เลือก)**
PE ปัจจุบัน = ราคาล่าสุด ÷ `eps_ttm`, PE ย้อนหลัง = ราคาปิดที่ปรับ split ÷ EPS 4 ไตรมาส ณ ไตรมาสนั้น, fair value = PE × `eps_ttm` ไม่ใช้จำนวนหุ้นในทุกขั้นของ PE ถ้า thaifin ปรับ EPS ย้อนหลังตาม split เหมือนที่ yfinance ปรับราคา PE จะไม่เปลี่ยนเมื่อแตกพาร์
ทางเลือกที่ไม่เลือก:
- EPS × จำนวนหุ้น ณ ไตรมาสนั้น แทน `net_profit` (คงระดับบริษัทไว้): ผิดเป็นเท่าตัวกับหุ้นที่แตกพาร์ เพราะ EPS ถูกปรับตามจำนวนหุ้นปัจจุบันแต่จำนวนหุ้นเป็นของ ณ ตอนนั้น (COM7 ×2)
- คง `net_profit` แล้วตัดไตรมาสที่ต่างจาก EPS × จำนวนหุ้นเกิน 10%: ไม่มีค่าผิด แต่เสียไตรมาสราว 15–20% ก่อนปี 2024 และตัดหุ้นที่แตกพาร์ซึ่ง `net_profit` ถูกอยู่แล้วทิ้งไปด้วย เก็บไว้เป็นแผนสำรองตาม D3
- Net Income ของ yfinance: มีแค่ 5–6 ไตรมาส ทำ band ย้อนหลัง 5 ปีไม่ได้

**D2 ราคาของ PE ย้อนหลัง = ราคาปิดสิ้นไตรมาสของ yfinance ที่ปรับ split แต่ไม่ปรับปันผล เก็บเป็นคอลัมน์ใหม่ `close` ใน market cap รายไตรมาส**
`quarterly_market_cap` คิดค่านี้อยู่แล้ว (`adjusted.groupby(...).last()`) แค่คืนออกมา ไม่ต้องดึงข้อมูลเพิ่ม PE band ยังใช้เฉพาะไตรมาสที่มี market cap เหมือนเดิม แม้ไตรมาสที่ไม่มีจำนวนหุ้น (ก่อน พ.ย. 2018) จะมีราคาแล้ว เพื่อให้ requirement "ป้ายเตือนข้อมูลย้อนหลังไม่ครบ" และการข้ามวันที่ของ backtest ยังถูกโดยไม่ต้องแก้ ขยาย band ไปไตรมาสก่อนหน้าได้ใน change แยกถ้าต้องการ
ทางเลือกที่ไม่เลือก: `close` ของ thaifin (ปรับตามปันผล spec ห้ามใช้), `mkt_cap ÷ shares` (เป็นราคาที่ซื้อขายจริง ไม่ปรับ split จึงไม่เข้ากับ EPS ที่ปรับแล้ว), ดึงราคา 5 ปีใน `YahooPrices` (ดึงซ้ำกับ `fetch_market_caps`)

**D3 ตรวจ EPS ก่อนแก้ code และหยุดถ้าไม่ผ่าน**
ตามกฎของ project field ใหม่ต้องเทียบก่อน สองส่วน:
1. EPS รายปี FY2022–FY2025 ของ thaifin (ผลรวม 4 ไตรมาส) เทียบ Company Highlights ของ SET สำหรับ PTT, COM7, HTC, SAWAD, BANPU, CHO, TOP, CPF, CPALL, KBANK (ผ่านเมื่อต่างไม่เกิน 0.01 บาทต่อไตรมาสจากการปัดเศษ หรือต่างตาม factor ของ split ที่เกิดหลังงวดนั้นพอดี)
2. ทั้งตลาดจาก cache: หุ้นที่ yfinance มี split ทุกตัว ไตรมาสก่อน split ต้องมี `net_profit` ÷ (EPS × จำนวนหุ้น) ≈ factor ของ split ที่เกิดหลังไตรมาสนั้น (EPS ถูกปรับแล้ว) นับจำนวนที่ไม่เข้าแบบนี้
ถ้าทั้งสองส่วนผ่าน ทำต่อตาม D1 ถ้ามีหุ้นที่ EPS ไม่ถูกปรับตาม split หยุดและถามผู้ใช้ว่าจะใช้แผนสำรอง (ตัดไตรมาสที่ไม่ตรงตาม D1) หรือแก้เฉพาะหุ้นเหล่านั้น บันทึกผลใน `engine/README.md` ไม่ว่าผลเป็นอย่างไร
ทางเลือกที่ไม่เลือก: เชื่อ EPS เพราะตรง SET ใน 4 ปีของ PTT (ไม่ครอบคลุมหุ้นที่แตกพาร์ ซึ่งเป็นเหตุผลที่ spec เดิมห้ามค่าต่อหุ้นจากแหล่งงบ)

**D4 เหตุผลของเกณฑ์ที่คำนวณไม่ได้ใช้ EPS**
"งบไม่ครบ 4 ไตรมาสสำหรับกำไร TTM" นับจาก EPS และ "กำไร 4 ไตรมาสติดลบ" ใช้ EPS 4 ไตรมาส ≤ 0 ข้อความเดิมคงไว้ ("กำไร" ยังถูกในความหมายของผู้ใช้) เงื่อนไข "ไม่มีจำนวนหุ้นล่าสุด" ไม่ใช้กับ PE band และ peer PE อีก แต่ยังใช้กับ PBV band และ Justified PBV
ทางเลือกที่ไม่เลือก: เปลี่ยนข้อความเป็น "EPS 4 ไตรมาสไม่เป็นบวก" (validator ไม่ให้เปลี่ยนชื่อ scenario และผู้ใช้อ่านคำว่ากำไรเข้าใจกว่า)

**D5 ตรวจผลด้วย backtest และ SET**
หลังแก้ code รัน `fair-value-backtest` ด้วย `--refresh` (cache เก่าไม่มีคอลัมน์ `close`) เทียบกับ `docs/backtests/fair-value-2026-10-15.md` และ spot-check PE ปัจจุบันของ PTT, COM7, SAWAD เทียบ P/E บน SET หลัง batch
ทางเลือกที่ไม่เลือก: เทียบ candidate list ก่อน/หลังจาก DB (DB เก็บแค่ run ล่าสุด ต้อง snapshot ก่อน ซึ่งทำได้แต่ backtest ครอบคลุมกว่า)

## Risks / Trade-offs

- **[แย่ที่สุด] thaifin ไม่ปรับ EPS ย้อนหลังตาม split ในบางไตรมาส (เช่น HTC 2019Q1) ทำให้ PE ย้อนหลังของไตรมาสนั้นผิดเป็นเท่าของ factor PE band median เพี้ยน และหุ้นอาจกลายเป็น candidate ด้วย MoS สูงเกินจริงโดยไม่มีใครเห็น** → D3 ตรวจทั้งตลาดก่อนแก้ code, `stock-sanity-check` จับ fair value > 5× ราคา และตารางค่าผิดปกติของ backtest
- **[แย่ที่สุด] thaifin เปลี่ยนความหมายของ EPS ในอนาคต (แหล่งไม่เป็นทางการ)** → `data-crosscheck` หลังอัปเกรด thaifin ตามกฎเดิม
- EPS ปัดเศษ 2 ตำแหน่ง: หุ้นที่ EPS 4 ไตรมาสต่ำกว่า 0.20 บาทได้ PE คลาดได้เกิน 10% → PE เกิน `max_pe` ถูกตัดอยู่แล้ว ที่เหลือยอมรับ (หุ้นกลุ่มนี้ผ่าน liquidity น้อย)
- หลังเพิ่มทุนมาก EPS 4 ไตรมาสลดตามจำนวนหุ้นถัวเฉลี่ย จึงตามหลังไม่เกิน 4 ไตรมาส fair value ของ PE band สูงเกินจริงช่วงนั้น (เดิมใช้จำนวนหุ้นหลังเพิ่มทุนทันที) → ป้ายเตือนโครงสร้างทุนเปลี่ยนยังแสดงเมื่อส่วนผู้ถือหุ้นเปลี่ยนเกินเกณฑ์
- หุ้นที่ `net_profit` เป็นสกุลเงินอื่น (BANPU) ได้ PE ถูกขึ้นถ้า EPS เป็นบาท แต่ ROE ยังผิด → นอกขอบเขต D3 ตรวจ EPS ของ BANPU ด้วย
- candidate list เปลี่ยนหลัง batch แรก ผู้ใช้อาจเห็นหุ้นหายหรือเพิ่มโดยไม่รู้เหตุ → apply หลัง batch ร่วมของ change อื่น (proposal Impact) และสรุปความต่างของ backtest ใน README

## Migration Plan

ไม่มี DB migration (market cap ไม่ได้เก็บใน DB) rollback ด้วย revert commit แล้วรัน batch ใหม่ cache ของ backtest ต้อง `--refresh` ทั้งตอนแก้และตอน rollback
